# 项目复盘

本人实际投入约 3 小时。实现与多数问题定位由 Codex 完成；本人负责选题与约束、配置真实模型、走读关键路径，并亲自复跑测试与场景后确认结论。下文是本人理解后的复盘，不把 AI 调试过程写成自己独立写代码的经历。

## 最难的工程问题

最难的是让「模型建议、用户确认、数据库事实」三者一致。模型可以提出候选时段，但不能自行授权 hard 改时，也不能把保存失败说成成功。只靠提示词不够，必须在副作用前和 `finish` 时用代码护栏卡住。

我复盘时印象最深的边界是：已经 `save_draft` 成功后，模型又去查别的时段，随后步数耗尽。如果最终结果按「最后一次查询」重算，就会把未保存时段写进答复。项目采用「保留已校验的保存快照」：预算/模型异常退出时报告已保存事实；正常 `finish` 仍核对当前结果与库。

另一类绕过是：结构合法，但把可保存候选删掉，以 `not_saved` 结束。`finish` 现在会检查是否仍存在合法空闲候选，有则要求先尝试保存。走读后我认为这比单纯加提示更可靠。

## 我学到什么

1. **ReAct 的证据在 Trace，不在故事。** 正常与冲突路径的工具顺序、建议时间、确认状态必须以当次 Trace 为准；步数会漂，不能拿旧跑次硬套。
2. **模型建议、代码定界。** hard 改时必须绑定素材与精确候选的可信确认；高风险不能靠「随便确认」放行；`draft_status` 只能来自真实 `save_draft` 返回与库记录。
3. **幂等要钉业务事实。** 参与哈希的是排期、风险码、确认等稳定字段，自由措辞和运行编号不应进 key；SQLite 事务 + UNIQUE 把「同请求一份草稿」落到存储层。
4. **Mock 与真实要分述。** Mock 适合故障注入、预算和护栏；真实模型才谈决策效果。109 项离线、10 Mock、10 真实应分开写，避免评审误解覆盖范围。
5. **未完成要显式。** 预算耗尽、模型错误、存储不确定时，保留已知事实与缺口，比假装「全部完成」更符合 Agent 产品预期。

## 真实模型与 Mock 的差异

本人复跑可见：同一用例 Mock 与真实步数不必相同（例如 normal 曾出现 Mock 5 步、真实 6 步），soft 冲突也可能同为 5 步但仍以当次 Trace 为准。真实路径额外覆盖了 hard、风险、失败、`slot_swap` 等。工具顺序不是脚本：可能多一次查询、确认或 finish 修正。

跟进首轮曾有待办匹配过严、已确认仍挂待办、验收计数把写入前拒绝算进去等问题；修正后真实 10/10，历史 Trace 保留在 `examples/history/`。结论仍限于当前配置与合成数据。

## 用时与边界

3 小时覆盖选题约束、配置、跟进沟通、走读与亲自复跑；不含把 AI 代跑时长算作本人加班。主体代码与多数修复仍由 AI 完成——这与「允许 AI、须如实记录个人贡献」一致。若面试追问，我可以依据走读与 Trace 解释：为何 hard 要精确确认、为何保存状态不能编造、为何预算退出要保留快照。
